# 版本间对比（HandleActionSignal）：
#   v1.4.0 → v1.5.0：耗时约 -29%、内存约 -27%、分配约 -12%（评论热路径零嵌套分配轻量解析）
#   v1.5.0 → v1.6.0：耗时约 -55%、内存约 -57%、分配约 -58%（外层 action signal 零分配轻量解析）
#
# v1.6.0 主要优化：
# 1) 外层 action signal 零分配轻量解析：原先每条弹幕批次都用标准 proto.Unmarshal 反序列化
#    整个 ZtLiveScActionSignal，其间会 reflect.New 出 50 个 ZtLiveActionSignalItem，并为其
#    Payload 拷贝出 [][]byte（pprof 显示该部分占 HandleActionSignal 分配量的过半，且是主要 CPU 来源）。
#    v1.6.0 新增 parseActionSignalItems / parseActionItem（见 fastdecode.go），仅提取每条 item 的
#    SignalType（field 1）与各 Payload（field 2，repeated bytes）元素，不构造任何 protobuf 消息，
#    也不对 Payload 做字节拷贝——直接以子切片视图传入内层解析。遇到任何非预期/截断的编码一律返回
#    ok=false，由 handleActionSignal 回退到标准 proto.Unmarshal，因此行为正确性不被破坏
#    （见 fastdecode_test.go 的 TestParseActionSignalItems / TestParseActionSignalItemsFallback，
#     快速路径与标准路径逐项比对一致，且覆盖字段乱序、单 item 多 payload、截断输入等情形）。
# 2) 解析逻辑共用与去冗余：原 handleActionSignal 内联的逐 signalType 分支被抽取为 handleActionItem，
#    快速路径与标准回退路径共用同一份解析逻辑，避免重复与漂移；事件分发快照去冗余、state/notify
#    对象池归还等 v1.5.0 的优化保持不变。下游排序与事件分发逻辑未变。
#
# 剩余分配的构成（v1.6.0，50 条评论/批次，约 151 allocs）：每条评论的 *Comment 结构体（1）、
# Content 字符串底层数组（1）、Nickname 字符串底层数组（1），合计约 3 allocs/条；这些是业务必需的
# 独立拷贝，已接近热路径下限。
#
# 关于池化与别名安全性的验证：google.golang.org/protobuf 在 Unmarshal 时会对 string 字段做拷贝；
# 快速路径同样通过 string(b[a:b]) 显式拷贝；外层解析仅传递 Payload 的字节视图（子切片），由内层解析
# 再显式拷贝出字符串，已派发的弹幕 DanmuMessage 持有独立拷贝，池化与复用均安全
# （见 alias_test.go: TestProtoStringAliasing）。
